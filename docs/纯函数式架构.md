# 纯函数式架构

## 目标

Prime 采用 **Functional Core, Imperative Shell（函数式核心、命令式外壳）**：

- Prime 自有的计算尽量写成纯函数；
- Minecraft、Vulkan、原生库和文件系统操作集中在边界层；
- 可变状态由单一所有者管理，并通过显式状态转移更新；
- 不为形式上的纯函数化显著增加运行时成本。

优先级是：**正确性 > 运行时性能 > 简洁性**。架构改造不得无依据地增加稳态内存、
GPU 工作量、CPU 流送成本或着色器寄存器压力。

## 术语

### 纯函数

纯函数的返回值只由参数决定，并且：

- 不读取时钟、全局单例或其他隐藏状态；
- 不执行 I/O、GPU 提交或资源生命周期操作；
- 不修改参数或共享状态；
- 相同输入在约定平台和二进制下产生相同输出。

纯函数不等于每次分配新对象。调用方可以复用缓冲区，但复用不得改变可观察结果。

### 不可变值

进入函数式核心的数据必须在其生命周期内保持不变。Java 对象身份、集合迭代顺序、
Vulkan 地址和 native handle 不得充当内容语义。

### 命令式外壳

命令式外壳负责不可避免的副作用：

- 读取 Minecraft 和 mod 状态；
- 读取时间、输入和配置；
- 创建、上传、提交、同步和销毁 GPU 资源；
- 调用 NRD、DLSS、FSR 等原生库；
- 文件、日志和调试捕获。

外壳应尽量薄，只负责校验、生命周期和调用顺序。算法留在函数式核心。

## 数据流

```text
外部状态
  → 命令式外壳：读取并校验
  → 不可变输入
  → 函数式核心：计算值、计划和下一状态
  → 命令式外壳：执行 GPU/native 操作
  → 成功后提交下一状态
```

外部边界不要求内部可重放。要求可重放的是：从显式 Prime 输入开始，到显式 Prime 输出
结束的自有模块。

## 边界

以下内容属于外部边界：

- `ClientLevel`、模型系统、资源包、Fabric renderer 和其他 mod 回调；
- biome tint、原版 light engine、方块实体和动态资源查询；
- Vulkan 驱动、GPU traversal、NRD、DLSS、FSR；
- 用户输入、墙钟时间、文件系统和日志。

边界层只捕获当前计算实际需要的数据，不复制整个外部系统。特别是：

- 不为形式完备冻结全部 biome、光照或任意 mod 状态；
- 不为离线重放常驻完整 CPU 场景或动态纹理副本；
- 不把闭源后端的内部历史伪装成 Prime 可控制的状态。

如果外部查询会影响 Prime 后续模块，其结果应在进入模块前固定为显式输入。无法低成本
固定的查询继续留在边界层，并在代码和测试中按外部依赖处理。

## 函数式核心

以下逻辑应优先保持纯函数：

- 已捕获场景数据的转换、面合并、材质翻译和内容编码；
- 帧参数、push constants 和 reconstruction 输入的计算；
- 随机数寻址和采样维度分配；
- 历史状态的比较、reset 判断和下一状态计算；
- ABI 编解码、内容指纹、语义校验和 replay 比较。

当前主要类型映射：

| 职责 | 不可变输入/结果 | 执行边界 |
| --- | --- | --- |
| 场景 | `VanillaSectionSnapshot`, `VanillaAssetSnapshot`, `CompiledCluster`, `WorldLightTreeInput` | `TerrainStreamer`, `TerrainScene` |
| 帧计划 | `IntegratorFrameInput`, `RealtimeFrameInput`, `ScreenshotFrameInput`, 对应 `*Plan` | `RealtimeFrameExecutor`, `ScreenshotFrameExecutor` |
| 重建 | `RawWavefrontFrame`, `PreparedNrdFrame`, `NrdFrameInput`, `NrdFramePlan` | `NrdDenoiser` 及各后端 |
| 历史 | `RealtimeSampleState`, `TemporalReconstructionState`, `NrdTemporalState` | 提交成功后的 commit |
| 重放 | replay codec、validator、comparator | `ReplayProbeController`, `ReplayProbeFrameExecutor` |

这张表表达职责，不要求为每一行创建额外抽象层。已有类能保持边界清晰时，不再包装。

## 状态与提交

状态更新采用常见的 **prepare/commit** 模式：

1. 已提交状态和当前输入生成执行计划；
2. 执行器消费计划并提交 GPU/native 工作；
3. 只有提交成功，候选状态才成为下一帧状态；
4. 失败、取消或仅录制的帧不得推进历史。

每类历史只有一个生命周期所有者。禁止由 renderer、后处理器和 native wrapper 分别维护
同一份 frame index、相机历史或 reset 状态。

资源句柄属于执行器；函数式核心使用稳定的内容 ID、版本号和不可变描述。资源替换采用
单调 revision，并由 timeline 或等价完成点决定退休时机。

## 确定性

Prime 自有模块遵守以下规则：

1. 随机样本由稳定的像素、样本、路径槽、bounce、分支和 seed 寻址。
2. 结果不得依赖活动队列索引、atomic 返回顺序、线程调度或墙钟时间。
3. 场景元素、材质、纹理、OMM 和灯光输入使用稳定排序。
4. 哈希和序列化不包含 Java 对象身份、GPU 地址、padding 或未初始化数据。
5. Shader 不得存在数据竞争；需要归约时使用固定顺序或与顺序无关的表示。
6. 完全重合 primitive 的 traversal 命中顺序不是有效契约。必须保留的叠层由场景构建阶段
   给出确定表示。

逐 bit 比较只在平台、驱动、shader、原生库、资源和配置指纹一致时成立。

## 性能规则

函数式架构是语义约束，不禁止以下实现：

- 对象池、arena、暂存缓冲和原地写入；
- GPU 图像别名、descriptor 复用和批量提交；
- 执行器内部的可变资源与延迟销毁；
- 不改变结果的缓存和增量更新。

正常渲染路径不得因为测试增加 readback、dispatch、图像副本或完整场景副本。调试功能在
未启用时只能有可忽略的检查成本。

新增稳态副本、跨帧缓存、GPU pass 或同步点前，必须说明热路径、内存/指令成本和预期收益。
若纯函数边界与性能发生明显冲突，停止实现并请求决策。

## 测试

测试按边界选择方法：

- 纯函数使用示例测试和属性测试，重点检查 NaN/Inf、范围、守恒、状态转移和 ABI；
- GPU 自有阶段使用低分辨率真实生产 shader，捕获实际阶段输出；
- 同平台确定性测试重复相同显式输入，并定位首个逐 bit 分歧；
- Minecraft、驱动和闭源 SDK 通过契约测试与集成测试覆盖，不验证其内部实现。

NRD/DLSS 测试验证 Prime 提供的输入、单位、坐标、资源分类、motion vector、reset 和提交
语义，不把降噪收敛能力作为单元测试目标。DLSS 输出不作为严格逐 bit 门禁。

`.prseq` 默认不进入版本库。只有重要、稳定、预计长期不变的回归案例，经确认后才作为
fixture 维护。fixture 不要求脱离 Minecraft 重建完整场景。

## 修改检查清单

提交新模块或重构前检查：

1. 这是纯计算还是外部副作用？副作用是否位于外壳？
2. 所有影响结果的 Prime 状态是否都是显式输入？
3. 输入是否在计算期间不可变？是否误用了对象身份或不稳定顺序？
4. 状态是否由单一所有者在成功提交后更新？
5. 是否能用属性测试或低分辨率真实 shader 检查高风险语义？
6. 是否增加稳态资源、额外 pass、同步或热路径分配？
7. 新抽象是否对应公认概念或实际职责？若只是换名或包装，不要引入。

## 当前有意保留的边界

- `RenderSectionRegion` 对 biome tint 和 light engine 的实时查询；
- Fabric/mod renderer 可能执行的动态查询；
- Vulkan traversal 和驱动调度细节；
- NRD、DLSS、FSR 的内部状态；
- replay 之外的完整 Minecraft 世界与资源状态。

这些不是待完成的“纯化缺口”。只有发生重要正确性回归，且解决方案不会严重增加稳态
成本时，才重新评估边界。
