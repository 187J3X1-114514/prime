## 性能：地形流送期间的 Java 堆分配风暴

- 状态：主要分配源已修复，仍需实机场景验证与 TLAS 更新策略研究
- 类型：CPU 地形构建存储与 TLAS 全量更新成本

### 现象

在较小 Java 堆的发行实例中，进入高视距世界并持续加载 Section 时，帧率会缓慢下降，最终因频繁 GC 接近卡死。手动提高 JVM 的最大堆可以显著延后并缓解问题；开发运行通常拥有更大的默认堆，因此不容易立即复现。

构建 JAR 中相关 Java class 与 SPIR-V 已和开发运行产物逐项核对，内容相同。这不是发行构建选择了不同代码或 shader permutation 导致的固定性能差异。

### 已确认原因

- Section 以小批次上传时，TLAS 实例表与 GPU TLAS 仍会针对全部驻留 virtual cluster 更新。
- CPU mesh 在 Section 输出合并成 4×4×4 virtual cluster 时使用有界 segment，避免创建一个与整个 cluster 等大的 Java 数组；原子上传仍需要与完整 generation 对应的 staging 和 GPU 分配。
- 大堆主要通过降低 GC 频率掩盖分配速率，不能解决算法复杂度、内存带宽或最坏情况下的停顿。

诊断中曾观察到约一百万个已分配的灯光树 `Bounds`、数万节点和约 4.6 万个单次 TLAS Section 实例。该统计包含尚未回收的不可达对象，说明的是分配风暴，不应直接解读为等量的永久泄漏。

当前实现已落地以下整改：

- 两级灯光树的 leaf、node、emitter 与 SAH 工作区均改为紧凑 primitive 数组；SAH 使用单次前缀/后缀聚合，fallback sort 不分配对象。
- 世界灯光树由渲染线程单独拥有稳定叶槽；普通替换、卸载与原点移动执行 O(n) refit，仅在容量、利用率或 SAH 成本明确退化时完整重建。
- mesh 三段合并只分配一次最终数组；GPU 上传后驻留对象只保留世界树所需的灯光摘要。
- 跨世界 worker 数量不会重置，worker/completed/ready 三阶段共享一个任务上限。一个 logical cluster 始终只生成一个 BLAS/TLAS instance，但 CPU 输入可拥有任意数量 segment；128K 三角形/约 16 MiB 只是 segment 工作集目标，不是内容拒绝上限。实际在途内存由内容规模和资源可用量决定，资源耗尽会明确失败而不会丢弃几何。

这些改动消除了已确认的无界存活堆与主要小对象风暴，但 TLAS 全量实例写入/GPU build 和 Section→cluster 的有界双份数组仍存在。

### 临时规避

在启动器中手动提高 Minecraft 的 JVM 最大堆（`-Xmx`），并根据机器物理内存保留足够的系统余量。该做法仅作为开发期临时方案，不应成为 Prime 的最终运行要求。

不要通过热路径调用 `System.gc()`、放宽无界队列或永久保留更大的中间缓存来规避问题。

### 重写要求

- 评估 TLAS `ALLOW_UPDATE`/refit 或低延迟批处理；不得让新 geometry 在可见性结构之外形成错误画面。
- 评估将 CPU segment 直接流式写入可复用 staging 区域，同时保持一个 cluster 只有一个 BLAS 和一次原子 resident 替换；不得以增加 TLAS instance 换取较低上传峰值。
- 在常见的小堆发行配置、高视距跑图和复杂发光地形下验证稳定分配速率、GC 停顿、队列上限及长期帧时间。

## 已知局限：水体介质最多嵌套两层

- 状态：接受，不修复
- 原因：扩大每路径介质栈会增加寄存器占用、热路径状态传递和 shader 编译/运行成本

Prime 当前的体积栈固定容纳两个非空气水体区域，并依赖水面法线正确、进入与退出形成
可解释的拓扑。玻璃和其他非水透明材质是逐面滤色器，不进入体积栈；因此玻璃与水叠放
不会消耗额外栈槽，从玻璃内部开始也不需要初始玻璃状态。

第三层水体区域无法入栈，此后的水中段吸收和 pop 顺序均不再保证正确。水体重叠、非流形
边界或遗漏界面同样不在支持契约内。相机初始介质只特殊识别水。

该限制不得被测试或文档表述为任意深度介质嵌套支持。除非未来有明确内容需求，并能证明紧凑
介质表示不会造成可测的寄存器、编译时间或运行性能回退，否则不扩大栈容量，也不引入动态栈或
介质身份匹配系统。

## 洞穴视距雾漏光

- 状态：已解决，关闭
- 修复前现象：洞穴内会出现不应存在的视距雾亮度；进入暗处后自动曝光逐渐提高，这部分错误
  亮度会随曝光一起变亮，因此比加入自动曝光前更严重
- 原因与已实现修复：旧 aerial perspective LUT 没有查询 Minecraft 地形局部遮挡。当时
  自动曝光最高 `+4 EV`，会把这项固定错误在显示端放大至 16 倍；当前最终自动曝光
  范围已经调整为 `[-8, +8] EV`。现在由五级、2.048 km 覆盖的
  RT 方向光深度 clipmap 沿视线积分位置查询太阳可见性；未知流式区域保守判为遮挡，不能
  重新制造漏光。实现与预算见[渲染实现：世界空间太阳体积阴影](渲染实现.md#世界空间太阳体积阴影)。
- 已接受边界：当前只求太阳方向，并以同一可见性近似调制大气 multiple scattering；它没有
  求半球天空可见性，也不是参与介质多次散射的无偏解。封闭洞穴、洞口、薄 cutout、地形
  流式替换、相机移动、太阳换向和远景复测已满足当前产品目标；这些模型边界不再作为漏光
  缺陷继续开放。
- 首次 GPU 回归暴露出太阳缓存 raygen 早于共享 RT descriptor set 中 RR、累积、大气和
  材质图像的首次布局转换。Validation 明确报告这些图像仍处于 `UNDEFINED`；初建中心
  tile 因而处于未定义行为且不会自动重追踪。现在所有共享 descriptor 资源先进入声明
  布局，大气自身图像也先转为 `GENERAL`，再调度太阳缓存。
- 64 倍大气探针继续暴露出两个流式状态问题：初建时已经扫过的 tile 被再次标脏后，旧状态
  要求 bank 先完成才允许修复、又要求无 dirty tile 才能完成，因而可能永久停在半成品；
  同时可读 bank 会先发布 `UNKNOWN` 再按 tile 修复，造成区块加载时大面积明暗闪烁。现在
  主覆盖完成后会继续消费 dirty mask；可读 bank 则在新 TLAS 发布后同帧精确重追踪合并
  变更区域，只有不可读 bank 保留渐进 tile 修复。
- 为检查剩余空间精度，aerial 体积已从 `32³` 提升到 `64×36×128`。深度线程改为只积分
  相邻中心之间的两个样本，再用有序并行前缀复合生成全部累计切片；这样保留 2.048 km
  覆盖并把最远层间距降到约 `31.8 m`，没有把旧的 16-step 全程积分复制到每个新 voxel。
  当前采用的高分辨率、视角中性大气探针已通过洞穴、远景和区块流送实机验收。

## 透明建模

玻璃按每个实际表面交点滤色，因此相接方块保留下来的内部面也会继续滤色；不同颜色玻璃
相接时会得到各表面因子的乘积。这是当前明确语义。若以后合并或剔除内部面，必须以实际
捕获几何和材质边界为依据，不能在 shader 中按颜色猜测拓扑。

确定性透明调度与直线 NEE 滤光同样是已接受的最终语义，不作为待修复缺陷。原因包括折射
链的光源连接问题、随机 Fresnel 分支对降噪历史的干扰，以及 MNEE、双向连接或专用引导
算法超出当前实时预算；完整边界见[透明渲染与实时重建](透明渲染与实时重建.md)。
